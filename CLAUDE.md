## Coding Standards

Write like a senior engineer. Minimal code that passes tests. No more.

### DRY — Don't Repeat Yourself
- Same logic appears twice → extract it. SQL CTE or dbt macro. Python helper function.
- Never copy-paste a block and change one value. Parameterize instead.
- dbt: repeated column logic → macro. Repeated test config → test severity defaults.

### KISS — Keep It Simple
- Simplest implementation that satisfies the requirement. No clever tricks.
- SQL: prefer readable CTEs over nested subqueries. One CTE per logical step.
- Python scripts: flat functions, no classes unless state is genuinely needed.
- Streamlit: one `@st.cache_data` per query, no caching framework on top of that.

### YAGNI — You Aren't Gonna Need It
- No abstractions for hypothetical future requirements.
- No config flags for features not being built this phase.
- No helper utilities "just in case". Write it when it's needed.
- No extra dbt models beyond what the dashboard actually queries.

### Concrete rules

```
DO:
  - Write the SQL that produces correct output, then stop
  - Add a test only when there is a real risk of that assertion failing
  - One function does one thing, named after what it returns
  - dbt model = one SELECT, CTEs for readability only

DON'T:
  - Add error handling for impossible states
  - Build a "data loading framework" when a 10-line script works
  - Add logging beyond what helps debug a real failure
  - Create base classes, mixins, or inheritance for 2 similar things
  - Add a --dry-run flag, --verbose flag, or any flag not used in tests or CI
  - Write docstrings that restate the function name
```

### Test-first, minimum implementation

1. Read the phase test file. Understand exactly what must pass.
2. Write the minimum code that makes those tests pass.
3. Stop. Do not add features the tests don't exercise.

If a test is too broad and forces over-engineering → narrow the test, not widen the impl.

## Workflow Rules

### Branch Strategy

**Before starting any work:**
```bash
git checkout stage
git pull origin stage
git checkout -b phase/<N>-<short-description>
# e.g. phase/1-foundation, phase/2-staging, phase/3-marts
```

Never work directly on `main` or `stage`.

### Commit Strategy

Each phase has multiple commits. Do NOT bundle a full phase into one commit. Split by logical unit:

- One commit per model added
- One commit per test suite added
- One commit per script or config added
- Documentation/schema YAML = separate commit from the model SQL

Commit format: `feat:`, `test:`, `docs:`, `chore:`, `fix:`

Example (Phase 2):
```
feat: add stg_yellow_trips model with casting and invalid trip filter
feat: add stg_taxi_zones model from seed reference
test: add schema tests for stg_yellow_trips (not_null, unique, accepted_values)
test: add custom SQL tests for fare and duration bounds
docs: add column descriptions for staging layer in schema.yml
```

### After Each Phase

1. Run full test suite for that phase (see phase docs below)
2. Run `dbt build --select <phase_selector>` — must exit 0
3. Run `pytest tests/ -v` — must exit 0
4. Update `progress.md` with:
   - What was done (models, tests, scripts created)
   - Exact `dbt build` output summary (X passed, 0 errors, 0 warnings)
   - What must be done next (next phase checklist)
5. Commit progress.md update
6. **End the session. Wait for manual verification before proceeding.**

### Test Consistency Rule

After each phase, run tests **twice**:
- First run: baseline
- Second run immediately after: confirm deterministic (same result, no flakiness)

If results differ between runs, investigate before ending the session.

### progress.md Format


## DuckDB Schema

```
raw layer (external views via read_parquet):
  raw_yellow_trips    — direct Parquet read, no copy

staging layer (dbt models, view materialization):
  stg_yellow_trips    — cleaned, cast, filtered
  stg_taxi_zones      — from seed

intermediate layer (dbt models, view materialization):
  int_trips_enriched  — joined with zones, derived columns

mart layer (dbt models, TABLE materialization):
  mart_daily_trips        — daily aggregates by borough
  mart_borough_revenue    — O-D revenue matrix
  mart_zone_performance   — per-zone composite score (0-100)
  mart_surge_analysis     — hour x day x borough demand heatmap
```
